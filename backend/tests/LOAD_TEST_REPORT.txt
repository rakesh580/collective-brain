================================================================================
  BOTTLENECK ANALYSIS
================================================================================

  1. SQLite Single-Writer Lock (Primary Bottleneck)
     ───────────────────────────────────────────────
     SQLite allows only ONE writer at a time. Under 1000 concurrent users,
     write contention causes timeouts. WAL mode + busy_timeout=30s mitigates
     this significantly (100% success up to 200 concurrent writers), but
     it's still the ceiling.

     Fix: Migrate to PostgreSQL for production. PostgreSQL's MVCC allows
     fully concurrent reads AND writes with connection pooling.

  2. Single Process / Single Worker
     ────────────────────────────────
     Tests ran with 1 uvicorn worker. The GIL limits CPU-bound operations
     to a single core. I/O-bound async operations scale well, but CPU-heavy
     graph/embedding operations block the event loop.

     Fix: Run with multiple workers (uvicorn --workers 4) + PostgreSQL.
     For WebSocket, use Redis pub/sub to broadcast across workers.

  3. Tail Latency Under Sustained Load
     ────────────────────────────────────
     P50 remains good (28-396ms) even at 1000 users, but P95/P99 spike
     because queued requests wait for the single writer lock.

     Fix: Read-write separation, caching hot paths (graph, members),
     and async task queues for non-critical writes.

================================================================================
  RECOMMENDATIONS FOR PRODUCTION (1000+ USERS)
================================================================================

  Priority 1 — Database
  ─────────────────────
  • Switch from SQLite to PostgreSQL (already supported in codebase)
  • Configure connection pool: pool_size=10, max_overflow=20
  • Add read replicas for heavy query endpoints (graph, analytics)

  Priority 2 — Application Server
  ────────────────────────────────
  • Run uvicorn with 2-4 workers (--workers 4)
  • Deploy behind a reverse proxy (nginx) with connection limits
  • Add response caching for expensive endpoints (/graph/full, /analytics)

  Priority 3 — Real-time Infrastructure
  ──────────────────────────────────────
  • Enable Redis pub/sub for cross-worker WebSocket broadcasting
  • Use Redis for session storage and rate limiting
  • Add WebSocket heartbeat/ping to detect stale connections

  Priority 4 — Monitoring
  ────────────────────────
  • Add request duration metrics (P50/P95/P99 per endpoint)
  • Monitor SQLite WAL file size / PostgreSQL connection pool usage
  • Set up alerts for error rate > 1% or P95 > 2s
  • Track WebSocket connection count per worker

================================================================================
  BUGS FOUND AND FIXED DURING TESTING
================================================================================

  1. SQLite StaticPool → NullPool
     Before: All requests shared ONE database connection → "database is locked"
     After:  Each request gets its own connection + WAL mode for concurrent reads
     Impact: Success rate jumped from 84.7% to 97.5% overall

  2. Health endpoint flooding LLM provider
     Before: /health/detailed made HTTP calls to LLM on every request
     After:  Reads circuit breaker state (in-memory, no HTTP)
     Impact: Eliminated all 503 errors under load

  3. Room creation returning 200 instead of 201
     Before: POST /rooms returned 200 (wrong REST semantics)
     After:  Returns 201 Created
     Impact: Test framework and clients can properly distinguish creation

  4. Room membership required for messages
     Before: Users couldn't send messages without being room members
     After:  Test properly adds all users to rooms (app behavior correct)
     Impact: DB write tests went from 10% to 100% success
